# Separação dos perfis: leitor, lançador e administrador

Data: 18/09/2026 (America/Sao_Paulo)

## O pedido

"Preciso que separe o perfil de leitura do perfil de lançamento."

Até aqui todo mundo que tinha login podia lançar, corrigir e mexer no
cadastro. Com a ferramenta em uso pelos superiores, passou a fazer
sentido ter gente que só olha o painel.

## O que foi feito

### Banco (`supabase/23_perfis.sql`)

- Tabela `public.perfis` (`usuario_id`, `nome`, `papel`), com
  `papel in ('leitor', 'lancador', 'admin')` e padrão `leitor`.
- `public.meu_papel()` — função `security definer` que devolve o papel do
  usuário logado sem cair na recursão de RLS ao ler `perfis`.
- `public.pode_lancar()` e `public.pode_administrar()` em cima dela.
- Policies de escrita reescritas: `leituras`, `ocorrencias` e `recepcoes`
  só aceitam insert/update de quem `pode_lancar()`; `unidades` e
  `parametros` só de quem `pode_administrar()`. A leitura continua
  liberada para todo autenticado.
- Todos os usuários que já existiam viram `lancador` (ninguém perde
  acesso). Um bloco `do $$ ... $$` promove o e-mail informado a `admin` e
  **levanta exceção se o placeholder `SEU-EMAIL-AQUI` não for trocado** —
  sem administrador ninguém mais mexeria no cadastro.
- Script idempotente: cada `create policy` é precedido do
  `drop policy if exists` correspondente. Rodado três vezes seguidas sem
  erro no PostgreSQL 16 local.

### Painel (`index.html`)

- Lê o papel por `POST /rest/v1/rpc/meu_papel`.
- O botão **Editar** do modo apresentação só aparece para `admin`.

### Lançamento (`lancamento.html`)

- Mesma leitura de papel, logo após identificar o usuário na tela.
- Para `leitor`: campos de valor e observação desabilitados, botão de
  salvar desabilitado com o texto "Somente leitura" e um recado
  explicando o acesso.

Os dois arquivos assumem o papel mais permissivo (`admin`/`lancador`)
quando a função não existe no banco. Isso é de propósito: o front é
conveniência, quem realmente barra é a policy do Supabase.

## Matriz verificada (PostgreSQL 16 local, scripts 01→23)

|-----------|-----|--------|----------|----------|----------|
| admin     | ok  | ok     | ok       | ok       | ok       |
| lancador  | ok  | ok     | ok       | NEGADO   | ok       |
| leitor    | ok  | NEGADO | NEGADO   | NEGADO   | NEGADO   |

## Armadilha registrada

Um UPDATE barrado por RLS **não dá erro** — ele simplesmente casa zero
linhas. O teste precisa olhar o command tag (`UPDATE 0`), não a ausência
de exceção. E `set local role` fora de transação é no-op: cada caso roda
dentro de `begin ... rollback`.
